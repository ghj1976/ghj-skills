# 踩坑与实测数据

下面这些问题都真实导致过重做。数字来自“AI 查公园”项目，按数量级理解，不要当成固定常量。

## 1. 逐句克隆会换说话人

**现象：**“声音时好时不好”——上一句低沉平稳，下一句突然变亮变快，像换了一个人。

**实测：** 45 个独立生成的 beat，基频中位数从 **71Hz 到 154Hz**；同一 prompt/reference 生成的 4 个长段是 **100 / 103 / 100 / 98Hz**。长段之间很稳，逐句不稳定。

**原因：** 零样本克隆会在每次生成开始时重新采样说话人特征。文本短、标点不同，模型自由度更大。

**修法：** 生成 3–4 个长段（每段 30–60 秒），同一 prompt cache、同一 seed、`inference_timesteps=10`。不要逐句重生成。用 `librosa.pyin(fmin=60, fmax=350)` 测每段，超出 85–115Hz 就重生成。

## 2. 语速快、音调高会显得不可信

**现象：**“语速太快了，让人感觉不信任。”

**实测：** 第一版 **7.8 字/秒**（1667 字、217 秒口播），基频约 171Hz；最终版 **5.2–5.6 字/秒**，基频约 95–105Hz。

**修法：** 低音 prompt/reference，文本已知、语气平稳，目标 5.2–5.8 字/秒。个别句仍超过 7 字/秒，就对该 beat 做轻微 `atempo`（0.85–0.95），绝不做变调。不要给整条混音加 `atempo=0.8`，停顿会变得不自然。

## 3. 按句切长段音频会丢字

**现象：**“话没说完，就切成另外一个了。感觉丢了段声音。”

**实测：**“它连轴转了十一天”实际占 1.5 秒；逐句切分只给了 **1.08 秒**，因为它切在附近的 RMS 最低点，把最后约 0.5 秒切掉了。

**原因：** 能量最低点不一定是句尾；切完再拼接还会引入人为空隙，并可能把尾音挪到下一段开头。

**修法：** 长段音频绝不切。段与段之间留空隙，ASR 只用来定**时间**。口播保持连续，最坏情况是字幕早/晚一点，绝不会少一个字。

## 4. ASR 对齐：切点必须是下一句开口

**现象：** 画面/字幕已经切了，上一句还能听见；或者字幕先出现、声音后到。

**修法：** 每个 beat 找到第一个匹配上的转写词；边界取**下一个 beat 第一个词的开始时间**。这就是“下一句已经开口”。不要切在停顿中点，也不要只按字数比例（TTS 一快一慢就漂）。

**实测：** 第一段的 ASR 对齐边界是 `[0, 6.2, 8.54, 10.96, 13.9, 16.52, 20.6, 27.8, 32.74, 37.94]`。9.54 秒的切点正好是下一句开口；旧的 7.67 秒切点把句子切断了。

## 5. 把 48kHz 数组直接喂给 Whisper

**现象：** faster-whisper 对中文语音输出英文乱码（“I said I don't know how”），时间戳还超过音频时长。

**原因：** faster-whisper 对 numpy 输入默认按 16kHz 理解。48kHz 数组被当成 16kHz，等于慢放 3 倍。

**修法：** `librosa.resample(y, orig_sr=48000, target_sr=16000)` 之后再 `model.transcribe`。改完中文转写就正常了。

## 6. ctranslate2 找不到 cuBLAS

**现象：** `RuntimeError: Library cublas64_12.dll is not found or cannot be loaded`。

**修法：** 用 CPU 跑 faster-whisper（`device="cpu", compute_type="int8"`）；3 分钟中文口播一两分钟就能对齐。也可以把 torch 的 `lib` 目录加进 PATH，但 CPU 更省事。

## 7. 图片切换时卡顿/冻结

最终版之前有四个叠加原因：

1. **停顿期间推拉被 clamp。** `progress = min(1, lt / beat_duration)`，而 0.34 秒空隙里 `lt` 超过了 beat 时长，画面冻结 0.34 秒，然后下一镜头突然跳。修法：用 `next_beat.start - start` 作为视觉时长，**线性**推进，切点前不 clamp。
2. **smoothstep 缓动。** `smoothstep` 在 t=0 和 t=1 速度为 0，每个镜头首尾都会近乎静止。修法：线性，或尾速度不为 0 的 ease-out。
3. **整数裁切。** `int(2048/zoom)` 每 2–3 帧才变一次，然后跳 1px。修法：`Image.transform(..., AFFINE, (sx,0,x0,0,sy,y0))`，用浮点值。
4. **叠化双影。** 两行大字或两张插画叠 0.2–0.3 秒，看起来像渲染故障。修法：硬切，用 whoosh 盖住。

**验证：** 解码 MP4，在切点附近取 36 帧，缩到 270×480 后算平均绝对差。修之前有 9–14 帧 diff <0.02（肉眼一样），随后一个 26–74 的尖峰；修之后 0 个冻结帧。

## 8. 静止文字卡被编码成冻结帧

即使整帧缓慢推近，18 秒场景只放大 7.5%，平均每帧约 0.004%，经常低于编码器更新阈值。文字卡于是会静止好几秒。

**修法：** 文字/数据版式加整帧缓慢推近 + 低透明度移动光扫。验收要看**解码后**的帧，不要看源帧。

## 9. 下划线穿过字形

**现象：** 橙色线从“一把钥匙”“自己想办法”的底部笔画中间穿过去。

**原因：** 中文字形墨迹会超出 em 框，`y + font_size + 22` 并不在字形下方。

**修法：**

```python
bbox = d.textbbox((x, y), text, font=f)
line_y = bbox[3] + 16
d.rectangle([x, line_y, x + width, line_y + 8], fill=accent)
```

## 10. 音效削波与响度漂移

音效轨按 RMS 0.02 归一，峰值仍然到 **1.0**，混音直接削波。修法：音效按**峰值**归一到 0.30，`amix` 后加 `alimiter=limit=0.95`，再用 `ebur128` 查真峰值。目标 −16 LUFS，峰值 ≤ −1.5dB。

## 11. CPU 版 PyTorch 看起来像 VoxCPM 的 bug

系统 Python 装的是 `torch 2.14.1+cpu`。VoxCPM 能跑，但 30 秒音频要 20 多分钟（约 40 倍实时），工具调用直接超时。这不是 VoxCPM 的问题。用 `--system-site-packages` 建 venv，补装 `torch/torchaudio +cu128`，桌面 GPU 上生成速度大约回到实时×0.3–2。

## 12. 导出的文章图片链接通常是坏的

Markdown 里常见 `assets/<标题>/file-*.png`，实际图片在文章目录。按**文章出现顺序**映射，然后逐张打开确认和段落对得上。不要只看文件名，也不要悄悄丢掉一张图。

## 13. 16:9 还是 9:16

第一版 16:9 在手机上被否。手机平台默认 1080×1920；16:9 只用于文章内嵌播放器或用户明确要求。旧版本单独放一个目录——用户明确说要并排对比。

## 14. 用户说“声音不符合预期”，但你也听不到

被否的第一版是低沉男声（基频 105Hz），用户要求换成另一条视频（`02/q1.mp4`）里的解说音色。问题在于：没法试听，只能靠量化指标判断“像不像”。

**做法：**

1. **从源视频抽音轨**，按 whisper 词级时间戳选 4–8 秒连续说话的片段，边界落在词的起止处（不切在字中间）。
2. **参考音频带 BGM 必须先去噪**。q1 的口播全程压着背景音乐，音节间隙的 RMS 只到 −17dB（干净人声应该在 −50dB 以下）。用 VoxCPM2 自带的 ZIP-Enhancer（ModelScope `iic/speech_zipenhancer_ans_multiloss_16k_base`）处理 prompt 和 reference，输出 16kHz，再峰值归一到 0.9。
   - 坑：本机 torchaudio 2.11 走 torchcodec，缺 shared FFmpeg DLL，`torchaudio.load` 直接抛 `libtorchcodec_core4.dll` 找不到。Gyan 的 ffmpeg 是静态编译，没有 DLL 可补。**修法**：`torchaudio.load/save` 换成 soundfile 实现（见 `make_voice_ref.py`），模型照常跑。
3. **量化验收**（`check_voice.py`）：段间基频极差 ≤25Hz、每段与参考的 LTAS 相关 ≥0.90、语速 4.5–6.5 字/秒。

**实测（q1 女声）：** prompt 基频 238.6Hz、reference 245.6Hz；四段生成 251.4 / 242.8 / 225.2 / 230.5Hz；LTAS 相关 0.978–0.990；旧的男声版与 q1 的 LTAS 相关只有 0.055——数值上能立刻区分“换对了”还是“还是那个人”。

**别硬套男声阈值。** 主流经验值“基频 85–115Hz”只适用于低沉男声；女声 225–251Hz 才是正常。判断标准应该是**段间稳定 + 与参考同音区 + 频谱相似**，不是绝对频段。

**语速要单独看。** q1 本身是短视频快节奏（6.4–6.9 字/秒），统一 0.92 倍 `atempo`（不变调）后落到 5.7–6.1 字/秒；`voice.json` 里的 `atempo` 由 `tts_chunks.py` 自动套用，原始长段存 `*_raw.wav`。不要把单个音色的问题用逐句变速去补。

## 15. 帧差单位搞错，会把正常慢镜头判成冻结

`qa_video.py` 早期版本这样算：

```python
a = np.asarray(Image.open(f).resize((270, 480)), dtype=np.float32)
d = np.mean(np.abs(a - prev))          # 0–255 尺度！
if d < 0.02: frozen()                  # 等价于 0.00008 归一化
```

阈值 0.02 看着像“5 个灰度级”，实际是 **0.02 个灰度级**。慢推拉在 270×480 上每帧只变 0.01–0.05 个灰度级，于是被反复判成冻结；而真正被否的版本里，冻结段的 diff 是 **0**。

**修法：** 帧差除以 255 归一化，冻结判据改成“连续 ≥3 帧完全相同（diff = 0）”，并把 `min_diff` 用 5 位小数打印出来。要更硬的证据，再用全分辨率逐帧比对：`identical_pairs` 必须是 0。

**教训：** 质检阈值要么有单位注释，要么直接引用归一化后的物理量；否则“通过/不通过”只是巧合。

## 16. “每节开头声音卡一下”——段首瞬态 + 长停顿叠在章节切换点

**现象：** 用户反馈“开头卡顿一下，每节时都卡顿一下，然后正常播放”，画面没问题，是声音。

**排查：** 把 `audio_mix.wav` 按 20ms 算包络，发现每段配音的**开头**都有一串固定形状：

```
-11 -18 -35 -47 -56 ...（约 40ms 的咔哒）→ 静音 0.3–0.4s → 正常说话
```

四个长段的瞬态完全一样，说明是 VoxCPM2 生成时的起手音。`build_audio_cont.py` 按 −45dB 裁首尾静音，
这段咔哒（−11dB）高于阈值，被当成“语音起点”保留了下来。而长段拼接点（每 2 个场景一段）
正好落在章节边界，于是每一节开头都是“咔—静半拍—再说”。

同一批音频里还有 0.9–1.0s 的句间长停顿（76 处 ≥0.12s 的静音，其中不少 0.5s+），听起来也像卡住。

**修法：** 新增 `clean_audio.py`（在 `tts_chunks.py` 之后、`align_asr.py` 之前跑）：

1. 先用 atempo 统一语速；
2. 用“连续 200ms 高于 −38dB”判定真正开口，裁掉段首 40ms 瞬态和其后静音（咔哒只有 60–80ms，不会通过 200ms 判定）；
3. 把 ≥0.55s 的静音压到 0.45s，拼接处 10ms 淡入淡出；
4. `build_audio_cont.py` 的段间空白从 0.65 收到 0.55。

修完实测：段首从 −11dB 起变成 −77 → −36 → −27 的自然起音；章节起点 ±80ms 内最大样本跳变 0.03–0.07（正常），没有咔哒；最长静音 0.42s。

**教训：** 拼接点要和章节切换点对齐，但拼接点上的“段首伪影”必须清掉——否则观众听到的是每一节都卡一下，还以为是画面问题。

## 17. 开头“刺啦”一声，以及段与段之间的音色漂移

**刺啦**：`sfx_track()` 在第一秒内放了两个噪声类音效（0.04s 的 impact、0.86s 的 whoosh），
而音乐从 0 秒才淡入到 −63dB。噪声冲击叠在淡入上，听起来就是开头一声“刺啦”。
修法：开头不放音效，让音乐淡入后直接开口；章节转场的 whoosh 保留但降到 0.45。

**音色漂移**：同一 prompt cache 生成 6 个场景 / 3 段时，出现过 263 / 248 / 224Hz（极差 39Hz）。
`check_voice.py` 会判 FAIL。不要用变调硬拉——换随机种子重生成偏差最大的段即可
（`regen_chunk.py 0,2 --seeds 20,21,22`，按基频接近参考 + LTAS 最高挑），实测收到 239 / 249 / 240Hz，
极差 9.8Hz。同一段不同种子的基频差异可达 40Hz，这是 VoxCPM2 长段生成的正常方差，不是参数错。

## 18. “太跳跃”与“信息量太大”，是同一个问题的两种表现

同一篇文章被否了三次：

1. 45 个短句版：每句一个结论，句间没有承接 → “内容太跳跃”。
2. 按段落重写后 54 个镜头、1196 字：句子连起来了，但塞了 5 条线 → “信息量太大，都没说透”。
3. 只讲一条线、34 个镜头、823 字：每段给足定义+对照+解释 → 通过。

**规则：** 一条主线讲透 > 五条线各说一句。判断标准是“这条线能不能给出定义、证据、反例各一句”；
给不出来就别放。删掉的行业跟进、三个自测问题、能力分层，在 2 分钟里只能一句带过，就是噪音。

## 19. 配图不是“有图就行”，是“这句和这张图对不对得上”

第一版按场景套默认图：6 万人名单配天平、现金牛配天平、问题一配资本流向图。用户一眼看出“图不对文”。

**做法：**
1. `script_data.py` 里用 `BEAT_IMG` 逐 beat 指定，`""` 表示不配图；
2. 图上自带中文标题时，先读标题再决定——标题和这句语义相反就不能用（“过去能顶四五年” vs “工具贬值快于人成长”）；
3. 30 多个镜头里有一半是数据/文字卡很正常；
4. 生成 `配图对照.png`（`contact_sheet.py`）逐镜头扫一遍，比在时间轴上拖动快得多。

**别名坑：** 按 beat 编号写映射时先数准每个场景有几个 beat（本轮按 9 个规划、实际 8 个，
导致“第三重”配到天平、“现金牛”配到三重交集）。写完 `print` 一遍 timeline 里的 `id/img` 再渲染。
